# Qwaste Bug Workflow

One bug at a time, all the way through, before touching the next one. Never batch two backlog items into one implementation pass — a half-fixed #4 sitting next to a half-started #5 is how a queue turns into an untestable pile.

## The six phases, per bug

### 1. Research
Before writing a plan or touching code:
- Read `.Codex/skills/qwaste-clean-code/SKILL.md` (and the files it points to — `QWASTE_CLEAN_CODE_AGENT_SKILL.md`, `CODE_STYLE_ASYNC_ERROR.md`) for the architecture/style rules that apply to whatever layer the bug lives in (service, type, page, component).
- For anything touching an API contract: read the **actual BE source** at `D:\Github\QWaste_BE\QWaste\QWastePlatform\QWastePlatform\src\main\java\com\example\QWastePlatform\modules\**` — the controller, its `Constants.Paths`, the request/response DTOs. This is ground truth.
- Only fall back to the internal docs site (`http://10.60.218.227:1234`) for narrative context (why a field means what it means, business rules) — it has drifted from the real code before (see the Space Monitoring `spaceLevel` gap found earlier). If BE source and docs disagree, BE source wins, and it's worth noting the doc is stale.
- Grep the FE for every consumer of what you're about to change (`grep -rln "<field/method/type name>" src`) — a rename or shape change almost always touches more files than the one bug report names.

### 2. Scope
Write down, in the same turn, before editing:
- What's actually broken (one or two sentences — the wrong assumption, not just the symptom).
- The exact list of files you expect to touch.
- What's explicitly *out* of scope this round (a sibling bug you noticed but isn't this item — note it for the backlog instead of fixing it inline).
Keep the fix to this scope. A backlog item is sized to be reviewable and testable on its own; scope creep here is what makes the next phase's diff impossible to gate cleanly.

### 3. Implement
Apply the fix per `qwaste-clean-code` conventions: typed, static service methods, `ENDPOINTS` constants for paths, no direct `axios`/`apiClient` from components, ready state handled by the caller not the service. Prefer keeping public service signatures stable (fix internals) when existing callers don't need to change, the way `SpaceService.getSpaceOverview` and `EnergyService.getElectricByFilter` were fixed without touching their pages.

### 4. Unit tests
Hand off to `.Codex/skills/qwaste-test-gate/SKILL.md` and run its full gate: typecheck, targeted tests, full suite, baseline diff. Do not skip this because "it's a small fix" — the totals/runtimeByStatus bug proved small-looking field changes have wide blast radius.

### 5. E2E check
No Playwright/Cypress exists in this repo yet, so this phase is a real browser check, not an automated suite:
- Use the `run` skill (or `npm run dev` directly) to start the app.
- Navigate to the actual page(s) the bug affects and exercise the golden path plus the specific broken case from the bug report.
- If the fix depends on a live backend behavior you can't reach from this environment, say so explicitly instead of claiming it was verified — don't assert an E2E check happened if it didn't.

### 6. Commit
One commit per backlog item, not one giant commit at the end. Message states what broke and why, references the item number from the backlog below. Follow the repo's existing commit style (see `git log`) and the `Co-Authored-By: Codex Sonnet 5 <noreply@anthropic.com>` trailer. This workflow treats "commit after phase 5 passes" as pre-authorized for items on the backlog below — still stop and ask before anything outside that (force-push, amending, touching branches).

After committing, check the item off in the Backlog section of this file (`- [ ]` → `- [x]`) so the queue state survives across sessions, then move to the next unchecked item.
